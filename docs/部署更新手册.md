# 部署与更新手册

> 场景：开发机打包 → **通过堡垒机手动上传** → 服务器执行更新脚本。
> 服务器不能直连外网、也不从 git 拉代码，所有变更以发布包形式交付。

---

## 0. 一次性准备（首次部署）

服务器已装好 Docker + NVIDIA 容器工具，并在 `/opt/spmcv` 有项目目录时，只需要：

```bash
cd /opt/spmcv
cp .env.example .env      # 按需改：GPU_ID、并发、限流
mkdir -p var/logs var/runs var/train_jobs
```

首次部署必须带数据（照片、模型之外的内容）：

```bash
# 开发机
bash deploy/package.sh --with-data
```

之后每次升级用默认包（不带 `data/`，几十 MB）。

## 1. 日常更新：三步

### 第 1 步：开发机打包

```bash
cd /Users/deepway/data/spmcv

# 常规升级（改了 app / web / deploy / docs）
bash deploy/package.sh

# 只打了少量文件：增量包，几十 KB
bash deploy/package.sh --since v3.0.0

# 改了 vision / ocr 代码或依赖（需要重建镜像）
bash deploy/package.sh        # 打包本身没区别，更新时加 --all
```

产物只有一个文件：

```text
dist/spmcv-release-v3.0-20261120_162531.tar.gz
```

包里有 `MANIFEST.txt`，记录版本、git commit、构建时间和文件清单。

### 第 2 步：通过堡垒机上传

把**这一个 `.tar.gz`** 上传到服务器，例如 `/tmp/`。
（WinSCP / SecureCRT 的 SFTP / 堡垒机文件传输都可以，位置随意。）

### 第 3 步：服务器执行更新

> 注意：必须带包路径。`bash deploy/update.sh` 不带参数只会打印用法后退出（不会改任何东西）。

```bash
cd /data/spmcv      # 或 /opt/spmcv，看你项目在哪
bash deploy/update.sh /tmp/spmcv-release-v3.0-20261120_162531.tar.gz
```

> 包内自带 `ENV.OVERRIDES`，脚本会把这 6 个部署参数合并进服务器 `.env` 并备份原文件，
> 所以**不用手工改 `.env`**。更新后核对一次即可（见 §5）。



脚本会：gzip 完整性检查 → 记录当前版本到 `var/backup/` → 解包覆盖 → **自动合并 `ENV.OVERRIDES`
到 `.env`（先备份 `.env.bak.<时间>`）** → 校验 compose → 构建镜像 → `up -d` → 等 `/healthz`
→ 跑 `deploy/verify.sh`（含契约检查）→ 打印版本与容器状态。
任何一步失败就退出，**构建失败时旧容器仍在运行**。

## 2. 验收（更新脚本已自动跑，也可手动）

```bash
cd /opt/spmcv
bash deploy/verify.sh http://127.0.0.1:8020 data/external/spec/01_车头及车牌号/*.png
```

输出应包含：

- `/healthz` 200、`/readyz` 的 vision/ocr 都 ok；
- 运行中模型版本（如 `v5.1.0`）；
- 契约版本 `v1`；
- `/v1/recognize` 返回 200/422 且响应只有 `scene/message/data`；
- 契约检查通过（含「多张接口已下线」校验）。

压测（在服务器上做，笔记本数字不作数）：

```bash
# 32 并发，目标 P95 < 5s
python3 scripts/bench_api.py --base http://127.0.0.1:8020 \
  --scene arrival_plate \
  --image data/external/spec/01_车头及车牌号/spec_image1.png \
  --vus 32 --requests 320 --max-p95-ms 5000
```

查看实时指标：

```bash
curl -s http://127.0.0.1:8020/metrics | grep -E 'in_flight|p95|requests_total'
curl -s http://127.0.0.1:8020/v1/meta | python3 -m json.tool
```

## 3. 回滚

代码回滚：**用上一版包重新执行一次更新**。

```bash
cd /opt/spmcv
bash deploy/update.sh /root/<上一版包>.tar.gz --no-build
```

建议保留最近 2 个包在服务器 `/root/`，体积不大（几十 MB）。

模型回滚：

```bash
curl -X POST http://127.0.0.1:8020/viz/api/model/activate \
  -H 'Content-Type: application/json' -d '{"version":"v5.0.0"}'
docker compose -f deploy/docker-compose.yml restart vision
```

每次更新前的版本信息都记在 `var/backup/last_update_<时间>.txt`。

## 4. 首次部署 / 换服务器

```bash
# 开发机：全量包（含 data/）
bash deploy/package.sh --with-data

# 服务器：解到 /opt/spmcv 后执行
cd /opt/spmcv
cp .env.example .env
vim .env            # GPU_ID 改成 nvidia-smi 里对应卡号；并发按机器规格
bash deploy/update.sh /root/<全量包>.tar.gz --all
```

前置条件：`nvidia-smi` 正常、`docker compose version` 可用、`models/current` 存在
（全量包自带 `models/`）。

## 5. 首次更新到 v3.0 后的一次性动作

v3.0 改了并发、限流、OCR 预算。包内自带 `ENV.OVERRIDES`，`update.sh` 会**自动合并**进服务器
`.env`（先备份 `.env.bak.<时间>`），只改这 6 项，不动 `GPU_ID` / SSO 等本机配置。
正常情况下**不需要手工改**；以下是核对与兜底方法：

```bash
cd /data/spmcv        # 项目实际路径
cp .env .env.bak
grep -E '^(MAX_CONCURRENT|RATE_LIMIT_PER_MIN|ADMISSION_WAIT_S|REQUEST_DEADLINE_S|OCR_BUDGET_S|OCR_PLATE_RETRY_S)=' .env.example
```

期望的 `.env` 片段：

```text
MAX_CONCURRENT=48
RATE_LIMIT_PER_MIN=3000
ADMISSION_WAIT_S=1
REQUEST_DEADLINE_S=5
OCR_BUDGET_S=2.5
OCR_PLATE_RETRY_S=1.0
```

旧的 `SEQUENTIAL_PHOTOS=6` 已不再使用，可删可留。

`update.sh` 已经会做 `up -d`（配置变了的容器会自动重建）。如果发现 OCR 容器没重建
（`docker inspect` 里还是 `--workers 2`），再手工强制重建一次：

```bash
docker compose -f deploy/docker-compose.yml up -d --force-recreate api ocr nginx
```

核对：

```bash
curl -s localhost:8020/v1/meta | python3 -m json.tool | grep -A6 limits
# max_concurrent 必须是 48，request_deadline_s 必须是 5.0

docker inspect spmcv-ocr-1 --format '{{.Config.Cmd}}'
# 应包含 --workers 4

docker inspect spmcv-ocr-1 --format '{{range .Config.Env}}{{println .}}{{end}}' \
  | grep -E 'OMP_NUM_THREADS|OCR_WORKERS|OCR_BUDGET_S'
# 应为 1 / 4 / 2.5
```

## 6. 项目名冲突（重要）

compose 项目名**已经固定在 `deploy/docker-compose.yml` 的 `name: spmcv`**，
`update.sh` 里也会 `export COMPOSE_PROJECT_NAME=spmcv` 并显式传 `-p spmcv`。

为什么必须固定：服务器上 `/data/deploy` 还跑着另一套 compose（容器名 `ongrid-*`），
它靠目录名推断项目名也是 `deploy`。如果我们的脚本不传项目名，就会用 `deploy`，
再带 `--remove-orphans` 时会把 `ongrid-*` 当成孤儿容器删掉（2026-11-20 真实发生过）。

因此：

- **不要**手工执行 `docker compose -f deploy/docker-compose.yml up -d --remove-orphans`；
- 手工操作时一律带项目名：`docker compose -p spmcv -f deploy/docker-compose.yml ...`；
- 万一又误删了其它项目，在其 compose 目录执行 `docker compose up -d` 即可恢复
  （`down` 未带 `-v`，命名卷和数据不会被删）。

## 7. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `包损坏或不完整（gzip 校验失败）` | 上传中断 | 重新上传整包 |
| 构建失败 | 依赖/网络 | 包未生效，旧容器还在跑；看 `docker compose build api` 报错 |
| `/healthz` 一直不 ok | api 起不来 | `docker compose logs api` |
| `/readyz` vision 不 ok | 权重缺失/GPU 没挂上 | `docker compose logs vision`，确认 `.env` 的 `GPU_ID` |
| 请求大量 429 | 并发或限流 | 看 `/v1/meta` 的 `limits`，调 `.env` 的 `MAX_CONCURRENT` / `RATE_LIMIT_PER_MIN` |
| 识别 422 变多 | 超时或识别不到 | 看 `/metrics` P95；OCR 慢就调 `OCR_BUDGET_S` |
| 想确认新代码生效 | 版本号 | `curl -s localhost:8020/v1/meta | python3 -c "import sys,json;print(json.load(sys.stdin)['version'])"`，应为 `3.0` |
