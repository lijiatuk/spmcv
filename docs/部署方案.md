# SPM 视觉识别 · 最终部署方案

日期：2026-11-16
适用：Linux + NVIDIA（L20 及以上）
交付形态：**Docker Compose 四容器**（nginx / api / vision / ocr）

---

## 一、架构

```
                    上层业务系统
                         │  HTTP
                    ┌────▼─────┐
                    │  nginx   │  :8020  统一入口 + 静态前端
                    └────┬─────┘
             ┌───────────┼───────────┐
             │           │           │
        ┌────▼────┐ ┌────▼────┐ ┌────▼────┐
        │   api   │ │ vision  │ │   ocr   │
        │  :8017  │ │  :8016  │ │  :8018  │
        │ 规则/编排│ │ YOLO+GPU│ │PaddleOCR│
        └────┬────┘ └────┬────┘ └────┬────┘
             └───────────┴───────────┘
                    共享挂载
          models/（权重）  data/（图片）  var/（产物）
```

**入口 8020**；8016/8017/8018 也可直连（上层系统按需选择）。

| 服务 | 镜像基础 | 作用 | 资源 |
|---|---|---|---|
| nginx | nginx:1.27-alpine | 反向代理 + 静态页 | 可忽略 |
| api | python:3.11-slim (+torch) | 业务规则、编排、控制台接口 | 2–4 核 |
| vision | pytorch CUDA 12.4 | 7 个模型头，**用 GPU** | 1 张 GPU |
| ocr | python:3.11-slim | PaddleOCR（CPU） | 4–8 核 |

## 三、部署步骤

### 1. 准备模型与数据（**最容易漏的一步**）

镜像里**不含权重和业务图片**，靠 volume 挂进去：

```bash
ls models/current/                     # 应指向 v5.x.x，含 7 个 .pt + manifest.json
ls models/pretrained/yolo26n-cls.pt    # 训练用的预训练权重
ls data/raw/recut/                     # 原始照片（唯一不可再生，务必备份）
```

模型校验（部署前跑一次，避免上线才发现权重缺失）：

```bash
python scripts/models.py verify --version v5.1.0
```

### 2. 配置环境变量

```bash
cp .env.example .env
```

`.env` 关键项：

```ini
# —— 对外端口 ——
HOST_PORT=8020

# —— 接口鉴权（内网可留空；对外必须设）——
API_KEYS=key-prod-xxxx,key-prod-yyyy

# —— 并发与限流 ——
MAX_CONCURRENT=8          # 同时处理的请求数，满了返回 429
RATE_LIMIT_PER_MIN=120    # 每个调用方每分钟上限
ADMISSION_WAIT_S=2        # 等不到并发槽位就快速失败，不排队

# —— 分析行为 ——
SEQUENTIAL_PHOTOS=6       # 6 张以内串行（结果稳定），超过才并发
REQUEST_DEADLINE_S=5      # 单图安全上限（不是目标延迟）
ENABLE_FUSION=0           # 辅助头未在新分布重训前保持关闭

# —— 可选：统一登录 ——
SSO_MODE=off
```

### 3. 构建并启动

```bash
docker compose --env-file .env -f deploy/docker-compose.yml up -d --build
```

首次构建 15–25 分钟（vision 的 CUDA 基础镜像很大）。国内默认走清华源，
海外可加 `--build-arg PIP_INDEX=https://pypi.org/simple`。

> **API 镜像大小取舍**：`deploy/Dockerfile.api` 有 `ARG WITH_TRAIN=1`。
> 1 = 带 torch，页面上能直接点训练（镜像 ~1.5GB）；
> 0 = 只做服务（392MB），训练改用 `docker compose exec vision ...`。

### 4. 验收（必须全绿）

```bash
SAMPLE_IMAGE=data/raw/recut/01_接车照片/01_车头及车牌号/<任一图>.png \
  bash deploy/smoke_compose.sh
```

它会依次检查：

1. 四个容器起来
2. `/healthz` 200
3. **容器内 `torch.cuda.is_available()` 为 True**（防止"以为用了 GPU 其实在跑 CPU"）
4. `/readyz` 三个下游都 ok、`model_version` 正确
5. 真跑一次 `/v1/check/arrival`（HTTP 200/422 都算链路通）
6. 接口契约检查（错误结构、错误码、`X-Request-Id`）

### 5. 压测（决定能不能上多个调用方）

```bash
python scripts/bench_api.py \
  --base http://127.0.0.1:8017 \
  --path /v1/check/arrival \
  --image <车牌图> --vus 4 --requests 100 --max-p95-ms 2000
```

**这一步必须在服务器上做**，本机（Mac/无卡）的数字没有参考价值。

## 四、上线后的日常操作

### 模型迭代（全在页面上）

```
数据集页：上传新一批 zip → 目录名自动映射到 12 类 → 自动标注
    ↓
快速标注：卡片网格看图，改标签（可批量）
    ↓
模型版本页：选数据/epochs → 开始训练 → 看进度和日志
    ↓
训练完成 → 「注册为候选版本」→ 填 v5.2.0
    ↓
「切换」→ 自动热加载，**不用重启**，立即生效
```

出问题一键回滚：切回上一个版本，同样即时生效。

### 训练在哪跑

| 环境 | 能否训练 |
|---|---|
| api 容器（`WITH_TRAIN=1`） | ✅ 页面直接点 |
| vision 容器 | ✅ `docker compose exec vision python scripts/train_scene_cls.py ...` |
| api 容器（`WITH_TRAIN=0`） | ❌ 返回 503 并提示原因 |

训练前要先生成数据集（服务器上）：

```bash
python scripts/build_union.py --fold 0      # 新旧合并，按工单分 5 折
```

## 五、容量与扩容

单张分析的耗时（L20 上预期，**需实测确认**）：

| 场景 | 典型耗时 |
|---|---|
| 油液 / 滤芯 | 0.1–0.3 s |
| 车牌 / 里程 | 1–2 s |
| 行驶证 / 车架 VIN | 2–3 s |
| 难读的图（跑满所有角度） | 4–5 s |

**扩容方式**：

1. **加 API 副本**：api 是无状态的（`--scale api=2~4`），nginx 自动轮询
2. **vision 是瓶颈**：单卡内模型锁串行，要提吞吐得加卡或用 TensorRT
3. **提前限流**：`RATE_LIMIT_PER_MIN` 按业务方分 Key 配置，别让一方打满

**接口返回 429 时的处理**：带 `Retry-After`，调用方退避重试即可。
`code=BUSY` 表示并发满，`code=RATE_LIMITED` 表示超频次。

## 六、运维

### 日志

```bash
docker compose --env-file .env -f deploy/docker-compose.yml logs -f api        # 每行带 request_id、耗时、状态
docker compose --env-file .env -f deploy/docker-compose.yml logs -f vision
```

### 监控

- `/healthz`：存活探针（只反映进程）
- `/readyz`：就绪探针（含 vision/ocr 可达 + 模型版本），**别用作容器健康检查**，会让下游抖动导致误重启
- `/metrics`：请求数/错误数/复核数/P50/P95

### 备份

| 对象 | 频率 | 说明 |
|---|---|---|
| `data/raw/` | 每日 | **唯一不可再生**，丢了就没了 |
| `models/` | 每次发版 | 含 manifest，回滚依赖它 |
| `var/feedback.sqlite3` | 每日 | 标注记录、改标计划 |

### 回滚

```bash
curl -X POST localhost:8017/viz/api/model/activate \
  -H 'Content-Type: application/json' -d '{"version":"v5.1.0"}'
# 立即生效，无需重启
```

## 七、常见问题

| 症状 | 原因 | 处理 |
|---|---|---|
| `smoke_compose.sh` 报 CUDA 不可用 | 没装 nvidia-container-toolkit | 装 toolkit，重启 docker |
| `/readyz` vision 不 ok | 权重缺失或 manifest 校验失败 | `docker logs vision`，看 "manifest 校验通过" |
| 所有请求 401 | 开了 `API_KEYS` 但没带 `X-API-Key` | 补头，或清空 `API_KEYS` |
| 返回 `TIMEOUT` + `degraded:true` | 单图超过 `REQUEST_DEADLINE_S` | 调大，或查 GPU 是否被别的任务占 |
| 同样输入结果不一样 | 多图并发抢 OCR | 设 `SEQUENTIAL_PHOTOS=6`（默认已开） |
| 页面还是旧样子 | 浏览器缓存 | 已设 `Cache-Control: no-store`，硬刷一次即可 |
| 训练报 503 | api 镜像没装 ultralytics | 用 `WITH_TRAIN=1` 重建，或改用 vision 容器 |

## 九、打包上传与端口验证顺序

### 打包

```bash
bash deploy/package.sh        # → dist/spmcv-<时间>.tar.gz，约 640MB
```

包含：`app web scripts tests deploy docs models data var`
排除：`var/runs`（训练产物）、`data/processed/*/cls`（软链数据集）、缓存、`node_modules`

**可选进一步瘦身**（如果服务器上不重训辅助头）：

```bash
# 92MB，只在不重训 group/action/bin_* 时可删
rm -rf data/processed/v5/heads
```

解包后在服务器重建数据集软链（秒级，不是重新拷贝）：

```bash
tar -xzf spmcv-*.tar.gz && cd spmcv
python scripts/build_union.py --fold 0
```

### 端口验证顺序（从外到内，出错最容易定位）

| 顺序 | 命令 | 期望 | 说明 |
|---|---|---|---|
| 0 | `docker compose ps` | 4 个容器 Up (healthy) | 有容器反复重启，先看 `logs` |
| 1 | `curl localhost:8020/healthz` | `{"ok":true}` | **nginx → api** 通了 |
| 2 | `curl localhost:8020/readyz` | vision/ocr 都 ok | **api → vision/ocr** 通了，且模型版本正确 |
| 3 | `curl localhost:8020/v1/meta` | 有 `contract` | 契约与模型信息 |
| 4 | `curl -o /tmp/c.json -w '%{http_code}' -X POST localhost:8020/v1/check/arrival -F "images=@图.png"` | 200/422 + `message` | 整条链路 |

**前 3 步不过时，用调试覆盖文件暴露内部端口逐层查**：

```bash
docker compose --env-file .env -f deploy/docker-compose.yml \
               -f deploy/docker-compose.debug.yml up -d
curl localhost:8016/healthz   # vision 单独
curl localhost:8018/healthz   # ocr 单独
curl localhost:8017/healthz   # api 绕过 nginx
```

> 8016/8017/8018 只绑 `127.0.0.1`，**不会暴露到外网**，验完记得用不带 debug 的命令重启。

### 常见"卡在第几步"

| 卡在 | 大概率原因 |
|---|---|
| 0 · 容器起不来 | 端口 8020 被占；或 volume 路径权限 |
| 1 · 8020 不通 | nginx 没起来 / `HOST_PORT` 不是 8020 |
| 2 · readyz 不 ok | vision 没拿到 GPU、权重缺失、ocr 还在加载模型（等 30s） |
| 4 · scan 报 TIMEOUT | `REQUEST_DEADLINE_S` 太小，或 GPU 被别的任务占满 |

## 十、端口清单与冲突检查

### 项目用到的全部端口

| 端口 | 用途 | 占宿主机 | 说明 |
|---|---|---|---|
| **8020** | nginx 对外入口 | ✅ | 控制台 + 业务接口统一入口（`HOST_PORT` 可改） |
| **8017** | api 直连 | ✅ | 上层系统可绕过 nginx 直接调 |
| **8016** | vision 直连 | ✅ | 只做模型推理，无业务规则 |
| **8018** | ocr 直连 | ✅ | 只做文字识别 |

> 服务器上 8080 / 18080 常被别的服务占用，所以默认入口改成 **8020**；
> 8016–8018 若也被占，用 `VISION_PORT` / `API_PORT` / `OCR_PORT` 改。

⚠️ **8016/8017/8018 直连端口没有鉴权**（vision/ocr 只有推理能力，不带业务判断）。
如果服务器不只在内网，务必：

- 用安全组 / 防火墙把这些端口限制到业务方 IP；或
- 只开放 8020（nginx），三个直连端口不对外；或
- 在 api 上配 `API_KEYS`（vision/ocr 仍需网络层保护）

### 主动出网（不监听端口）

| 目标 | 用途 | 默认 |
|---|---|---|
| `10.51.13.7:8008` | KEV 系统 | 已关闭（`KEV_MODE=off`） |
| `10.51.13.7:8013` | VLX 识别 | 已关闭（`USE_VLX=0`） |
| PyPI / 镜像站 443 | 构建时拉依赖 | 必须通，否则构建失败 |

### 部署前体检

```bash
bash deploy/check_ports.sh            # 默认查 8020 + 8016/8017/8018
HOST_PORT=8021 API_PORT=9017 bash deploy/check_ports.sh
```

输出会告诉你：端口是否空闲 / 被谁占用、docker 与 compose 版本、GPU 是否可见、
以及 firewalld / ufw 的放行命令。

### 上传后的完整部署命令

```bash
# ① 上传（本地执行）
scp dist/spmcv-*.tar.gz user@<server>:/opt/

# ② 登录服务器解包
ssh user@<server>
cd /opt && mkdir -p spmcv && tar -xzf spmcv-*.tar.gz -C spmcv && cd spmcv

# ③ 端口体检（先做，避免起服务才发现冲突）
bash deploy/check_ports.sh

# ④ 配置
cp .env.example .env
vi .env
#   默认：HOST_PORT=8020（入口）、API_PORT=8017、VISION_PORT=8016、OCR_PORT=8018
#   端口被占就改这里；对外调用按需填 API_KEYS

# ⑤ 重建数据集软链（几秒，不复制图片）
python3 scripts/build_union.py --fold 0

# ⑥ 构建并启动（首次 15–25 分钟）
docker compose --env-file .env -f deploy/docker-compose.yml up -d --build

# ⑦ 验收
SAMPLE_IMAGE=$(ls data/raw/recut/01_接车照片/01_车头及车牌号/* | head -1) \
  bash deploy/smoke_compose.sh

# ⑧ 压测（确认延迟达标）
python3 scripts/bench_api.py --base http://127.0.0.1:8020 \
  --path /v1/check/arrival \
  --image "$SAMPLE_IMAGE" --vus 4 --requests 100 --max-p95-ms 2000
```

⑦ 全绿才算部署成功；⑧ 的数字才是能对外承诺的延迟。

## 十一、访问入口

部署完成后**直接访问 `http://<服务器IP>:8020/`** 即可，会自动进控制台，不用记 `/ui/console.html`。

| 地址 | 内容 |
|---|---|
| `http://IP:8020/` | 控制台（自动跳转） |
| `http://IP:8020/docs` | Swagger 接口文档（可直接试调） |
| `http://IP:8017/` | 同上，绕过 nginx 直连 api |
| `http://IP:8017/healthz` · `/readyz` · `/metrics` | 健康与监控 |

### ⚠️ compose 不会自动读根目录的 `.env`

compose 文件在 `deploy/` 下，Docker 只在**第一个 compose 文件所在目录**找 `.env`。
所以所有命令都要显式带 `--env-file .env`：

```bash
docker compose --env-file .env -f deploy/docker-compose.yml up -d --build
```

漏了这个参数，`HOST_PORT` / `GPU_ID` / `API_KEYS` 都会退回默认值——
表现为"端口还是 8080""还是用了 0 号卡"，很难查。`smoke_compose.sh` 已经内置。

## 十二、指定 GPU

`nvidia-smi` 里的编号就是 `GPU_ID`：

```ini
# .env
GPU_ID=4
```

改完重建（只重启不改镜像）：

```bash
docker compose --env-file .env -f deploy/docker-compose.yml up -d
docker exec $(docker compose --env-file .env -f deploy/docker-compose.yml ps -q vision) \
  python -c "import torch;print('可见卡数',torch.cuda.device_count(),torch.cuda.get_device_name(0))"
```

期望输出 `可见卡数 1 NVIDIA L20`。如果显示 8 张，说明 `--env-file` 漏了。

## 十三、镜像为什么这么大 / 磁盘够不够

### 体积构成

| 镜像 | 大小 | 里面是什么 |
|---|---:|---|
| vision | **~9GB** | CUDA 12.4 runtime + cuDNN + cuBLAS（基础镜像解压后 ~7.5GB）+ ultralytics |
| api（WITH_TRAIN=1） | ~1.5GB | python-slim + torch(CPU) + ultralytics |
| api（WITH_TRAIN=0） | ~400MB | python-slim + fastapi |
| ocr | ~1.2GB | python-slim + onnxruntime + OCR 模型 |

**大头是 CUDA**，不是我们的代码。CUDA runtime 镜像本身就有 3.3GB 压缩 / 7.5GB 解压，
这是跑 GPU 推理的必要成本，换任何框架都一样。

想省空间：

```bash
# API 不带训练能力（省 1GB）
docker compose --env-file .env -f deploy/docker-compose.yml build --build-arg WITH_TRAIN=0 api
```

### 磁盘预留

```
镜像          ≈ 12GB（vision 9 + api 1.5 + ocr 1.2）
构建缓存      ≈ 8GB
数据集/模型   ≈ 1.5GB
训练产物      ≈ 每个实验 200–500MB（可清理）
────────────────────────
建议预留      ≥ 30GB，宽裕 40GB
```

构建前先体检：

```bash
bash deploy/preflight.sh
```

它会检查磁盘、内存、GPU 空闲显存、端口占用，不够就直接告诉你，不会让你等 20 分钟再失败。

### 清理构建缓存

```bash
docker builder prune -f          # 清构建缓存（不删镜像）
docker image prune -f            # 清悬空镜像
docker system df                 # 看占用明细
```

### 构建慢怎么办

| 慢在哪 | 处理 |
|---|---|
| 拉 CUDA 基础镜像 3.3GB | 配 Docker 镜像加速器，或先 `docker pull` 单独拉 |
| apt-get 卡几分钟 | 已默认换阿里云源（`--build-arg APT_MIRROR=deb.debian.org` 可还原） |
| pip 拉包慢 | 已默认清华源 |
