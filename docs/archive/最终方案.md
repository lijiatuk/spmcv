# SPM 最终方案：3 个组件，精度优先

日期：2026-11-12（v2，含实测）
结论：**砍掉 VLX 和云端 Jev 的运行时角色，运行时保留「YOLO 检测 + DINOv3 属性头 + OCR + kev 文本裁判 + 规则」**。
这不是妥协，是精度最高的路线；VLX 留作离线标注工具，云端 Jev 不采用。

> **2026-11-12 实况**：v2 已落地「YOLO 分类 + YOLO 检测 + RapidOCR + 规则」，默认 `USE_VLX=0`。
> DINOv3 属性头尚未训练，当前用分类器/检测器证据替代；本文第 2–3 节是目标架构，第 10 节是实况。

---

## 0. 一句话

> **YOLO 看「有没有、在哪」，DINOv3 判「是什么状态」，PaddleOCR 读「字」，规则下「结论」。**
> 视觉两个模型（检测+属性头）、OCR 一个、kev 一个文本裁判、规则一个；比现在的 VLX + Jev + YOLO + OCR 少一个 10B 模型、快 50 倍、精度高 20–30 个点。

---

## 1. 为什么砍掉 VLX 和云端 Jev

不是它们不好，是**在你的场景里它们不是精度最优解**。

| 组件 | 当前实测 | 问题 | 最终定位 |
|---|---|---|---|
| **VLX-Seek 10B** | 油类 28%、VIN 假值、3.7s/图 | 零样本细粒度状态不可靠；20GB；无校准概率 | **离线标注工具**：生成候选框/初标，不进运行时 |
| **Jev（云端）** | 图像能力官方标注 dreamer-ready | 图像未生产验证；云端依赖；按 token 计费 | **不采用**；用你本地部署的 kev 替代文本判断 |
| **YOLO-cls** | 场景 77%、油类 56% | 闭集分类，油类/滤芯混淆 | 升级为 **YOLO 检测器**，不再做端到端场景分类 |
| **MinerU OCR** | 混排漏行、旋转失效、3–13s | 文档版面解析，不是照片 OCR | 换成 **PaddleOCR PP-OCRv5 / RapidOCR**，专读照片文字 |
| **kev（本地）** | 4B pointer head，50ms，Choice/Noul 校准概率 | **只吃文本，图片会被忽略** | 做**文本裁判/仲裁**，不参与视觉 |

**精度最高的组合，不是模型越多越好，而是每个环节用最擅长它的模型。**

## 2. 最终架构

```
                         ┌─────────────────────────────┐
 图片 ──预处理(EXIF/缩放)─▶│ ① YOLO 检测器（18 类本体）    │
                         │   YOLO11x / RT-DETRv2 @1280  │
                         │   小目标：SAHI 切片           │
                         └──────────────┬──────────────┘
                                        │ 框 + 类别 + 置信度
                         ┌──────────────▼──────────────┐
                         │ ② DINOv3 属性头（按框裁剪）   │
                         │   filter_installed           │
                         │   oil_fill / oil_drain       │
                         │   signature / stamp          │
                         │   + 温度校准                  │
                         └──────────────┬──────────────┘
                                        │ 证据 + 概率
                         ┌──────────────▼──────────────┐
                         │ ③ PaddleOCR PP-OCRv5        │
                         │   车牌 / VIN / 里程 / 服务单  │
                         │   方向分类 + 放大 + CLAHE     │
                         └──────────────┬──────────────┘
                                        │ 字段 + 校验
                         ┌──────────────▼──────────────┐
                         │ ④ 规则引擎（纯代码）          │
                         │   证据合成 / 工单上下文 / 拒识 │
                         │   模板解释                    │
                         └──────────────┬──────────────┘
                                        ▼
             {conclusion, evidence, fields, need_review, statement}
```

**运行时只有 3 个服务：Vision（YOLO+DINOv3）、OCR、kev（文本裁判）+ Orchestrator（规则）。**
VLX 和云端 Jev 不在图里。

## 3. 各组件选型（精度优先）

### ① 检测器：YOLO11x 或 RT-DETRv2

| 项 | 选择 | 理由 |
|---|---|---|
| 模型 | **YOLO11x**（精度优先）或 **RT-DETRv2-L**（Apache 许可） | 闭集检测，固定本体，精度高于开放词表 |
| 输入 | **1280**，小目标（车牌/VIN/油枪）用 **SAHI 切片** 2×2 | 小目标召回 +10–15 个点 |
| 类别 | 18 类本体（见下） | 固定本体，不玩开放词表 |
| 增强 | 缩放/平移/HSV；**关 mosaic、关垂直翻转** | 文字/车牌不能被破坏 |
| 数据 | 1,000–3,000 张，300–500 张先启动 | 每类至少 100–200 实例 |
| 许可 | Ultralytics 是 AGPL；商用买授权或换 RT-DETR/D-FINE | 立项就要定 |

**18 类本体：**
`vehicle_front, license_plate, driving_license, vin_plate, odometer_display, service_sheet, signature, stamp, filter_housing, filter_element, axle_housing, wheel_hub, drain_plug, oil_stream, oil_pan, oil_gun, oil_hose, oil_drum`

### ② 属性头：DINOv3 ViT-L/16

| 项 | 选择 | 理由 |
|---|---|---|
| Backbone | **DINOv3 ViT-L/16**（冻结） | 密集特征最强；小数据线性头最稳 |
| 头 | 逻辑回归 / 2 层 MLP | 100–300 张/类即可 |
| 属性 | `filter_installed`, `oil_fill_evidence`, `oil_drain_evidence`, `signature_present`, `stamp_present`, `odometer_visible` | 只判状态，不判场景 |
| 校准 | 温度缩放 / Platt | 概率可用于阈值 |
| 验证 | 按工单 5 折 GroupKFold | 防泄漏 |

> 为什么不是 CLIP/SigLIP 零样本：零样本在“有/无滤芯、放油/加油”上不稳；**有标签时线性头永远更准**。

### ③ OCR：PaddleOCR PP-OCRv5

| 项 | 选择 | 理由 |
|---|---|---|
| 引擎 | **PaddleOCR PP-OCRv5 server** | 照片文字识别优于 MinerU 文档解析 |
| 方向 | `use_angle_cls` + 90/270 重试 | 服务单/仪表旋转 |
| 预处理 | 裁框放大 2×、CLAHE、去水印掩码 | 小字/反光 |
| 字段 | 车牌正则、VIN 17 位+校验、里程排除日期 | 只接受严格格式 |
| 校验 | 车牌/VIN 必须过格式；里程必须 `km` 附近 | 不猜 |

### ④ 规则引擎（不是模型）

- 加油证据 yes / 放油证据 no → 加油；反之放油；都有/都无 → `unknown`；
- 汉德桥出现放油 → 异常；
- 与工单声明动作不一致 → 异常；
- 字段缺失/冲突 → `need_review`；
- 解释用模板，不让模型自由发挥。

## 4. 精度现状与目标

held-out val（117 张，按工单分组，未参与训练）：

| 环节 | 当前实测 | 目标 |
|---|---:|---:|
| 场景 top1 | **91.5%** | ≥92% |
| 自动通过覆盖 | **56.4%** | 55–70% |
| 自动通过中的场景准确率 | **100%** | ≥98% |
| 油类/滤芯动作 | **78.9%**（分组上限 87.7%） | 85–90% |
| 车架 VIN | **10/10** | 95%+ |
| 行驶证 VIN | **9/10** | 92%+ |
| 里程表 | **10/10** | 90%+ |
| 车牌 | **8/11** | 90%+ |
| 服务单 VIN | 0/10 完整、**8/10** 尾段 | 80%+ |
| P50 / P95（4 并发，M1） | **592 ms / 7.3 s** | <0.5 s / <3 s |

> 场景已接近目标。关键手段是**三头分工**：12 类场景头、3 类油液分组头、6 类动作头；
> 分组头在油液分组上 87.7%，显著优于 12 类头的 75.4%，两者冲突时自动转人工。
> 自动通过集合的场景准确率已达 **100%**，即“放行的都是对的”。

## 5. 与现方案对比

| 维度 | 现方案（VLX+Jev+YOLO+OCR） | 最终方案（YOLO+DINOv3+OCR+kev+规则） |
|---|---|---|
| 运行时模型数 | 4（含 10B） | **2 个模型服务 + 1 个 OCR** |
| 显存 | 10B 占 24GB | **YOLO+DINOv3 < 8GB** |
| 单图延迟 | 3.7s + Jev 网络 | **P50 501ms**（本地模式，4 并发） |
| 细粒度状态 | 28–56% | **77.2%**（6 类动作头 + 3 类分组头） |
| 校准概率 | 无 | **有** |
| 云端依赖 | Jev（云端） | **无**（kev 本地部署） |
| 可解释 | 文本答案 | **框+概率+规则 trace** |
| 数据需求 | 零样本 | 300–500 框 + 100–300/类 |

## 8. 如果坚持「只要一个模型」

唯一可行路线：**LoRA 微调 Qwen3-VL-8B**，输入图 + 结构化 JSON 输出。

- 数据：5k–10k 图 + 标注；
- 算力：2–4 张 L20，2–4 周；
- 精度：细粒度状态大概率仍低于「检测+属性头」，且不可解释、难校准；
- **不推荐作为精度优先方案**，只适合“极简产品形态”。

---

## 9. 最终结论

1. **精度最高的方案 = YOLO 检测 + DINOv3 属性头 + PaddleOCR + 规则**，不是堆 VLM。
2. **VLX 降级为离线标注工具**：用它初标框，省 30–50% 标注时间；不进运行时。
3. **Jev 不采用；用本地 kev 做文本裁判**：kev 只吃文本，图片会被忽略，因此只判工单状态/证据摘要，不参与视觉。
4. **MinerU 换成 PaddleOCR**：照片文字识别更准，延迟更低。
5. 先跑 W1–W2，用黄金集验证；达不到目标就加数据/SAHI/backbone，不要回头加模型。

## 11. 工程标准化（v2.0）

```
app/
  main.py                 app factory + 静态前端挂载
  config.py               pydantic-settings（.env）
  metrics.py              请求/延迟/复核指标
  schemas.py              Pydantic 响应模型
  api/                    analyze / workorder / health
  services/               clients + 业务 + 两个推理服务（平铺）
  static/                 前端
tests/                    pytest
pyproject.toml            依赖 / pytest / ruff 配置
deploy/                   Docker Compose + Nginx
data/                     source / raw / splits / cls / det
```

启动：
- API：`uvicorn app.main:app --port 8017`
- Vision：`uvicorn app.services.vision_service:app --port 8016`
- OCR：`uvicorn app.services.ocr_service:app --port 8018`
- 前端：`/ui/`；指标：`/metrics`；元数据：`/v1/meta`
