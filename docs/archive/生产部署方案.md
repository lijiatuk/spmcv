# SPM 视觉接口 · 生产部署方案

版本：v1.1（2026-11-12，按实测硬件与"无法独占 GPU"更新）
适用：内网单机 GPU 服务器，对上提供 HTTP 接口，服务间调用（无 C 端用户）
目标：**高精度 + 低延迟 + 可回滚 + 可查证**，不追求分布式架构

---

## 0. 一页结论

| 项 | 结论 |
|---|---|
| 部署形态 | 单机 Docker Compose（nginx + api×3 + vision×1 + ocr×1[8 worker]），不引 K8s |
| GPU | 无法独占 → **共享 GPU 5**（空闲 21.8 GB）。vLLM 是预分配显存、SM 空闲，所以损失的是 P99 尖刺而非平均性能 |
| CPU | 208 核 / 1 TiB 内存 → **OCR 留在 CPU 多进程**，不抢 GPU；32 核配额换稳定的低尾延迟 |
| 精度 | 不动模型，保持现有 7 个权重；**冻结成 manifest + 打进镜像** |
| 延迟 | 共享卡下目标 P50 ≤150 ms、P95 ≤1.2 s、P99 ≤3 s；做 3 项改造后可达 |
| 吞吐 | 8–12 图/s（≈3–4 万图/小时），远超业务量级；瓶颈是尾延迟不是吞吐 |
| 许可 | 推理层去掉 `ultralytics`（AGPL），改 ONNX Runtime（MIT）交付；训练仍可离线用 |
| 数据 | 不建库；**JSONL 文件日志**（请求流水 + 结果流水），30 天保留 + 轮转 |
| 基线 | git 首个 commit + `tag v5.0.0`；镜像按 tag 发布，回滚 = 换 tag |

**必须先做、先于一切的三件事**：git 基线、GPU 绑卡 + 压测定基线、权重进镜像。这三件不做，后面所有工作都是空中楼阁。

## 2. 目标与 SLO

### 2.1 服务等级目标

| 指标 | 目标 | 现状（M1 MPS，4 并发） |
|---|---|---|
| 单图 P50 | ≤ 150 ms | 592 ms |
| 单图 P95 | ≤ 1.2 s | 7.3 s |
| 单图 P99 | ≤ 3 s | — |
| 整单（5 图）P95 | ≤ 4 s | — |
| 错误率（5xx） | < 0.1% | 无统计 |
| 可用性 | 99.5%（单机，允许计划内重启） | 无 |

> 与独占 GPU 相比，P95 从 800 ms 放宽到 1.2 s——这是"无法独占"的直接代价，用 §3.3 的绑卡 + 限额策略来吸收，而不是靠堆代码。
> P99 允许 3 s：共享卡上别人 vLLM 的生成尖刺会周期性撞上来，这个抖动**修不掉，只能监控**。真要压下去只有独占一途。
> 超时后的行为是**降级返回**（`need_review=true`、`fields=null`），不是挂连接等——所以超时阈值本身就是 SLO 的一部分。

### 2.2 精度基线（不退化）

沿用现有 held-out val（117 张，按工单分组）指标作为回归门槛：

| 环节 | 基线 | 允许下限 |
|---|---|---|
| 场景 top1 | 91.5% | ≥ 90% |
| 自动通过覆盖 | 56.4% | ≥ 55% |
| 自动通过中场景精度 | 100% | 100%（**误放行零容忍**） |
| 油类/滤芯动作 | 78.9% | ≥ 78% |

### 3.2 本项目的显存需求

| 组件 | 权重 | 运行时占用 |
|---|---|---|
| 场景分类 12 类（yolo11n-cls） | 3 MB | — |
| 油液分组 3 类 | 3 MB | — |
| 动作 6 类 | 3 MB | — |
| 组内二分类 ×3 | 9 MB | — |
| 检测器 18 类（yolo11s） | 18 MB | — |
| CUDA context + cuDNN workspace | — | ~1.5 GB |
| 640×640 批 8 激活峰值 | — | ~1.5 GB |
| **合计** | **~36 MB** | **< 4 GB** |

结论：**一张卡放得下 5 个本项目副本**，显存完全不是约束；约束是 **SM 争抢导致的 P99 抖动**。

### 3.3 共享卡策略（无法独占）

**关键事实：`GPU-Util` 全是 0%，但显存各占 16–44 GB。**

这说明 vLLM 是**启动时一次性预分配 KV cache**，显存被占 ≠ SM 被占。空闲时我们能拿到几乎全部算力，只有对方真正在生成 token 的那几十毫秒里才会争抢。也就是说：**共享卡的代价不是"一直慢"，而是"偶发尖刺"**——P50 几乎不受影响，受损的是 P99。

所以策略是「**绑卡 + 显存限额 + 压测判定**」，而不是预先降级：

```yaml
  vision:
    environment:
      CUDA_VISIBLE_DEVICES: "5"                 # 宿主机第 5 张
      VISION_DEVICE: "cuda:0"                   # 容器内可见的第 0 张（不是 5）
      VISION_MAX_BATCH: "8"                     # 争抢严重时降到 4 或 2
      VISION_MEM_FRACTION: "0.35"               # ≈16 GB 上限，留 5 GB 余量给别人
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              device_ids: ["5"]                 # 关键：不是 count: 1
              capabilities: [gpu]
```

| # | 措施 | 理由 |
|---|---|---|
| 1 | **绑 GPU 5** | 空闲 21.8 GB 最多；上面的 kev 是自家服务，被挤时好协调（GPU 0 上是 3 个别人的 vLLM，难谈） |
| 2 | 显存限额 0.35 | 我们实际只要 <4 GB，留足余量避免"对方扩容 → 我们 OOM"。torch 阶段用 `torch.cuda.set_per_process_memory_fraction`；ONNX 阶段用 CUDA EP 的 `gpu_mem_limit` 选项 |
| 3 | 启动时 warm-up 推理 | 把 cuDNN / ORT 图优化那 2–3 s 放到启动期，别进用户请求 |
| 4 | batch 可配（8→4→2） | 压测发现 P99 抖 >3×P50 时，牺牲吞吐换稳定性 |
| 5 | FP16 + 算子融合 + IOBinding | torch 阶段 `half=True` / `model.fuse()` / `inference_mode`；ONNX 阶段导出 fp16 + `io_binding`。单次前向 ~15 ms → ~5 ms，占 SM 时间越短越不容易被撞上 |
| 6 | **不要用 MIG** | L20 的 MIG 会把显存和 SM 一起切碎，640 输入的检测不划算 |

> 第 2、5 条两套写法对应两个阶段：**P0–P1 还是 torch/ultralytics，P5 ONNX 化后换成 ORT 等价配置**。迁移时这两项必须一起改，否则限额不生效、显存又回到无保护状态。

**升级判定标准**（写进压测报告，别凭感觉）：

| 压测结果（8 并发，5 分钟） | 结论 |
|---|---|
| P99 ≤ 2×P50 | 共享无碍，维持现状 |
| P99 介于 2–4×P50 | 降 batch 到 4，再测 |
| P99 > 4×P50 或 P95 > 1.5 s | 带着 `nvidia-smi dmon` 数据去申请独占卡 |

前置条件（服务器上确认）：`nvidia-container-toolkit` 已装、`docker compose` ≥ v2.20、`docker info | grep -i nvidia` 有输出。已确认 Docker 29.4.3，满足。

### 3.4 CPU 与 OCR 容量规划（208 核的真正价值）

服务器 **208 核 / 1 TiB 内存**，这是本方案最被低估的资源。它直接改了两个决定：

**决定一：OCR 不上 GPU，留在 CPU 多进程。**

理由：GPU 是共享的、有尖刺；OCR 是 CPU 密集型且**可线性扩展**。208 核里拿 32 核给 OCR，能得到比共享 GPU 更稳定的尾延迟，还完全不占显存。把 GPU 全部留给视觉前向（那部分不可替代）。

**决定二：OCR 的"多角度重试"不再是延迟问题。**

现在 15 遍串行是 P95 的元凶。有了并发余量，可以改成「**并行发起 + 命中即取消**」：一次把 4–8 个变体同时丢进 OCR 池，谁先出结果用谁，其余丢弃。延迟 = 1 遍（~120 ms），而不是 15 遍（~2 s）。

| 服务 | 副本 × worker | CPU 配额 | 线程模型 | 说明 |
|---|---|---|---|---|
| nginx | 1 | 2 | — | 纯转发 |
| api | 3 × 1 | 每副本 2 核 | asyncio | 全是等下游 I/O + 一次 PIL 解码 |
| vision | 1 × 1 | 8 核 | 解码线程池 + GPU 微批 | PIL 解码吃 CPU，别只给 2 核 |
| ocr | 1 × **8** | **32 核** | 每 worker `intra_op=4` | 8 个并发 crop 槽位 |

容量估算：8 槽 × 单 crop ~120 ms ≈ **66 crop/s**；单图平均 3 个 crop → **理论 20 图/s**。按目标 8–12 图/s 设计，留 2 倍余量应对尖刺。

注意事项：
- 每个 OCR worker **独立加载一份 RapidOCR**（PP-OCRv5 server rec ≈ 300 MB/进程），8 进程 ≈ 2.4 GB —— 1 TiB 内存下无感，但别开 64 个 worker。
- `OMP_NUM_THREADS` / `intra_op_num_threads` 必须**显式设成 4**。不设的话 onnxruntime 默认按核数开线程，8 个进程 × 208 线程会造成严重的线程超订，性能反而塌掉。
- 容器加 `cpus: "32"` 限流，做同机其他服务的"好邻居"；同机有多个 vLLM，别把 208 核全吃了。
- 磁盘：`/data` 795 GB、`/data2` 816 GB 可用，应用放 `/data/spmcv`；Docker 数据根在 `/`（330 GB 可用），镜像 + 日志够用，但**别把训练数据搬进来**。

## 3.5 对外接口：按素材目录分三类

产品给的素材分三个目录，业务上也是三段独立校验，所以对外给三个接口：

| 接口 | 目录 | 核心规则 |
|---|---|---|
| `POST /v1/arrival` | `01_接车照片` | 行驶证 VIN 与车架 VIN **必须一致**；车牌/里程缺失即复核 |
| `POST /v1/repair` | `02_故障及修复照片` | 同一场景出现矛盾结论 → 复核；汉德桥出现桥放油 → 复核；汉德桥不做轮胎/滤芯判定 |
| `POST /v1/inspection` | `03_项目检查表` | 首页 VIN 允许仅尾段；末页必须有签字 + 盖章 |

统一响应：`{ok, reasons[], photos[], unexpected[]}`。`unexpected` 是"传错类的照片"，
不会让整单失败，但会在响应里点名——这是调用方最容易犯的错。

旧的 `/v1/analyze`（单图）与 `/v1/workorder`（跨类整单）保留，供内部与调试使用。

## 4. 部署拓扑

```
                    上层应用 ──▶
                    ┌──────────────────────────────────────────────┐
                    │ nginx · IP 白名单 + API Key + 限流           │
                    └──────────────────────┬───────────────────────┘
                                           │
                 ┌─────────────────────────┼─────────────────────────┐
                 ▼                         ▼                         ▼
        ┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐
        │ api #1           │      │ api #2           │      │ api #3           │
        │ 1 worker         │      │ 1 worker         │      │ 1 worker         │
        └────────┬─────────┘      └────────┬─────────┘      └────────┬─────────┘
                 └─────────────────────────┼─────────────────────────┘
                                           ▼
                    ┌──────────────────────────────────────────────┐
                    │ vision · GPU 5（共享）                       │
                    │ 单实例 · 微批 ≤8 · 模型常驻                  │
                    └──────────────────────┬───────────────────────┘
                                           ▼
                    ┌──────────────────────────────────────────────┐
                    │ ocr · CPU 8 worker / 32 核                   │
                    │ 变体并行 + 命中即取消                        │
                    └──────────────────────────────────────────────┘
```

> 注意：**单图内部是串行的**——文字类场景必须先 `detect` 拿到框、再裁剪送 OCR，没法并行。并行只发生在两个层面：整单多图之间（`asyncio.gather`）、以及 OCR 内部的多个变体之间（T3）。所以 `ocr` 的并发能力必须够，否则整单会被最慢的那张图卡住。

### 4.1 为什么 api 是「单 worker × 3 副本」而不是「1 容器 3 worker」

现方案 `Dockerfile.api` 用 `--workers 2`，但 `app/metrics.py` 的计数器是**进程内**的：Prometheus 每次只能抓到其中一个 worker，请求数漏计一半，P95 更是两个不相交样本里随机取一个。同理 `MAX_CONCURRENT` 的 `asyncio.Semaphore` 也是 per-worker，真实并发 = 2×4 = 8，不是你以为的 4。

→ **每个容器 1 个 worker，靠副本数和 nginx 做并发**。进程数少了，但语义正确、可观测、可扩缩。

**为什么 OCR 反而要多 worker**：OCR 没有跨请求共享的指标状态，进程隔离对它只有好处。8 个 worker 各自持有独立的 RapidOCR 会话，才能真并行；单进程靠 `threading.Lock` 串行是现在 P95 失控的根源。

### 4.2 端口

| 服务 | 容器端口 | 宿主暴露 | 说明 |
|---|---|---|---|
| nginx | 80 | `8080`（或直接 80） | 唯一入口 |
| api | 8017 | 不暴露 | 仅内部 |
| vision | 8016 | 不暴露 | 仅内部 |
| ocr | 8018 | 不暴露 | 仅内部 |

**不要给 vision/ocr 映射宿主端口**——现 compose 没映射是对的，保持。

### 4.3 nginx 必改项（现配置有 3 个实际缺陷）

| 缺陷 | 后果 | 修法 |
|---|---|---|
| 声明了 `keepalive 64` 但没开 `proxy_http_version 1.1` | 上游连接**永远不复用**，每请求一次 TCP 握手 | 加 `proxy_http_version 1.1;` + `proxy_set_header Connection "";` |
| `client_max_body_size 25m` | `/v1/workorder` 上传 5–12 张手机原图很容易超 25 MB → **413** | 全局 `200m`，`/v1/analyze` 单独 `20m` |
| 无 `gzip`、无安全头、无 `/metrics` 隔离 | 前端首屏大、指标裸奔 | `gzip on; gzip_types text/css application/javascript application/json;` + `/metrics` 白名单 |

```nginx
upstream spm_api {
    server api:8017;
    keepalive 64;
}
location /v1/ {
    limit_req zone=api burst=40 nodelay;
    proxy_pass http://spm_api;
    proxy_http_version 1.1;          # ★ 缺这行 keepalive 就是废的
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Request-Id $request_id;
    proxy_read_timeout 70s;          # 略大于整单预算 60s
    proxy_send_timeout 70s;
}
location = /metrics {
    allow 127.0.0.1;
    allow 10.0.0.0/8;
    deny all;
    proxy_pass http://spm_api;
}
```

## 5. 镜像与模型交付

### 5.1 许可证：必须把 AGPL 从运行时摘出去

事实：权重是你们自训的，但 `ultralytics` 库本身是 **AGPL-3.0**。AGPL §13 规定"通过网络提供服务"即触发源码提供义务，所以**只要这个接口对外（哪怕只对兄弟系统）提供服务，就有义务**。当前 `deploy/requirements-vision.txt` 直接装了 `ultralytics`，等于把 AGPL 代码带进了交付物。

推荐路径（**2 天，精度不变**）：

1. 训练侧继续用 `ultralytics`（离线、内部、不分发）。
2. 发布前导出 ONNX：
   ```bash
   # 分类头（scene / group / action / binary×3）
   yolo export model=runs/cls_v1/weights/best.pt    format=onnx imgsz=640 half=True
   # 检测头（内嵌 NMS，服务端不用自己写后处理）
   yolo export model=runs/det_v1/weights/best.pt    format=onnx imgsz=640 half=True nms=True
   ```
3. 推理容器只装 `onnxruntime-gpu`（MIT），**不装 `ultralytics`、不装 `torch`**。
4. 验收：117 张 val 上 ONNX 与 `.pt` 的 top1 逐张一致率 ≥ 99%，mAP 差异 < 0.5 点。

> 法务提醒：ONNX 化能消除"运行时分发 AGPL 代码"的问题，但 AGPL 对"用其训练出的权重"的解释存在争议。**内部自用风险最低；若要对外销售，请法务出书面意见**，或走 5.3 的彻底路径。

彻底路径（2–3 周，仅当法务要求）：检测换 **RT-DETRv2 / D-FINE**（Apache-2.0），分类换 **timm**（Apache-2.0）backbone + 线性头。代价是重训 + 重新标框，不建议现在做。

### 5.2 模型版本化（`models/` 注册表）

之前的问题是：`runs/` 下 28 个 `best.pt`，靠 7 个环境变量拼路径，**同一份代码 + 不同的 `.env` = 不同的产品**。

现在改成注册表模式，**服务只认一个变量 `MODEL_DIR`**：

```
models/
  registry.json          # 版本索引：状态 / 指标 / 创建时间 / manifest 指纹
  current -> v5.0.0      # 软链，服务默认加载这个
  v5.0.0/
    manifest.json        # 每个文件的 sha256 + 来源 + 指标
    weights/*.pt         # 7 个训练权重
    onnx/*.onnx          # 6 个分类头（可选，torch-free 推理用）
```

**进 git**：`registry.json`、`*/manifest.json`、`README.md`
**不进 git**：`*/weights/`、`*/onnx/`（由发布流程投递，见 §5.3）

#### 服务加载顺序（`app/services/vision_service.py`）

1. 单个显式 env（`VISION_WEIGHTS` 等）—— 兼容旧部署，生产不要设
2. **`MODEL_DIR/weights/<role>.pt` —— 推荐**
3. 历史默认路径（`runs/...`）—— 只在本地开发命中

生产只需：

```bash
MODEL_DIR=models/current      # 容器内 /app/models/current
```

#### 切版本 / 回滚

```bash
python scripts/models.py list                 # 看版本、指标、当前指向
python scripts/models.py verify               # 校验 sha256
python scripts/models.py freeze v5.1.0 --from runs/candidate --metrics reports/metrics_v51.json
python scripts/models.py activate v5.1.0      # 上一个 active 自动变 previous
docker compose restart vision                 # 重启生效
```

回滚就是把 `activate` 换回上一个版本，**不改任何环境变量**——这是注册表相对"7 个 env"的核心收益。

#### 状态机

| 状态 | 含义 | 谁在用 |
|---|---|---|
| `candidate` | 刚冻结，未验证 | 无人，等 A/B |
| `active` | `current` 指向 | 服务 |
| `previous` | 上一个 active | 回滚目标（至少保留 1 个） |
| `archived` | 已淘汰 | `prune` 删除 |

#### 硬性规则

- **七个头必须同版本一起产出**：混搭不同版本的 scene/action 会让融合阈值失去意义。
- 启动必须校验 sha256，不一致 → **启动失败**（不是 warn）。这一项还没实现，见 `reports/code_review.md` H4。
- 切版本前先 `verify`。
- 候选权重先跑 `scripts/eval_heads.py`，指标不低于基线才 `activate`。

## 6. 性能设计（本方案的核心）

### 6.1 先看清瓶颈在哪

**问题一：每张图 5–8 次 HTTP + 5–8 次全量解码**

`app/api/analyze.py` 里，一张图的最小调用链：

```
scene → (低置信再 3 次 scene 旋转) → group → binary → action → detect → OCR(1~15 次)
```

每次调用都 `_read(await image.read())`，即 `PIL.open + exif_transpose + convert("RGB")`。4000×3000 手机原图单次解码 **50–80 ms**，6 次就是 **300–500 ms**——这就是 P50 592 ms 的主要构成，跟 GPU 计算几乎无关。

**问题二：OCR 的 15 遍串行重试 = P95 的全部**

`app/services/ocr_service.py` 车牌路径的 `variants`：
- 4 个角度（0/90/270/180）
- + 2 对比度 + 2 锐化 = 8
- + 4 个带框再试 = 12
- + 3 次 PP-OCRv5 server 放大重试 = **15**

而且 `ocr_text()` 外面套了全局 `LOCK`，**完全串行**。单遍 100–300 ms（server 更慢）→ 15 遍就是 2–4.5 s，叠加重试就是 7 s。P95 7.3 s 是这么来的，不是模型慢。

**问题三：视觉侧全局锁 + 无批处理**

`vision_service.py` 所有 `predict` 都在 `with LOCK:` 里，8 个并发请求排队串行。L20 上一个 640 分类前向 ~3–5 ms，锁 + Python 开销把它放大到 15–20 ms，GPU 利用率实际 < 15%。

### 6.2 改造项（按 ROI 排序）

#### T1. 视觉合并成单次调用 `/v1/frame`（收益最大，1–2 天）

一次上传、一次解码，服务端内部把所有需要的头跑完：

```
POST /v1/frame  (image)
→ { scene: {...}, group: {...}, action: {...}, binary: {axle,tire,filter},
    detect: {...}, frame: {w,h}, model_version }
```

orchestrator 端不再分别调 5 个接口。省掉 4–6 次解码 + 4–6 次 HTTP + JSON 往返，**P50 预计 -40% 到 -50%**。

同时保留旧的 5 个接口用于灰度，等 `/v1/frame` 稳定再下掉。

#### T2. 微批推理（1–2 天）

视觉服务内部改成队列 + 微批：

```python
# 伪代码
QUEUE: asyncio.Queue = asyncio.Queue(maxsize=256)

async def worker():
    while True:
        batch = await collect( QUEUE, max_n=8, max_wait_ms=10 )
        frames = [b.img for b in batch]          # 一次解码的结果复用
        with torch.inference_mode():
            probs = CLS.predict(frames, imgsz=640, half=True, verbose=False)
        for b, p in zip(batch, probs):
            b.future.set_result(p)
```

- 批量上限 8、等待窗口 10 ms：空载时延迟只加 10 ms，满载时吞吐提升 3–5 倍。
- 队列满 → **立即 429 + `Retry-After`**，不要无限排队（无限排队会把 P99 拉到 30 s，比拒绝更伤上游）。
- `half=True`（FP16）+ `torch.inference_mode()` + `model.fuse()`：L20 上指标提升 20–30%。
- 启动后跑一张 dummy 图 warm-up，避免首请求吃 cuDNN autotune 的 2–3 s。

#### T3. OCR 并行化（2 天，P95 的决定性改造）

**不上 GPU**——OCR 留在 CPU，理由见 §3.4：208 核可以线性扩，而共享 GPU 有尖刺。

1. **拆掉全局 `LOCK`**：`ocr_text()` 外面那把锁把所有 OCR 串成一列，这是 P95 失控的根源。改为每 worker 独立会话 + 多进程（8 个），锁自然消失。
2. **变体并行 + 命中即取消**：把原来的 15 遍串行改成 `asyncio.as_completed` 并发发射，第一个命中字段的结果胜出，其余 `cancel()`。延迟 = 1 遍（~120 ms），不是 15 遍。
3. **早停顺序按命中率排**：0° 原生 → 0° 放大 → 90° → 其余。实测大部分失败来自曝光/裁剪，不是角度，所以顺序比数量重要。
4. **显式线程配额**：每 worker `intra_op_num_threads=4`、`OMP_NUM_THREADS=4`。不设的话 onnxruntime 会按 208 核开线程，8 进程互相超订，性能直接塌。
5. **缓存**：同一 `(image_sha256, box, keep)` 命中 LRU（容量 2000），工单重复提交直接返回。

> 只有在 CPU 方案仍达不到 P95 目标时，才考虑把 PP-OCRv5 server rec 放 GPU（单遍 100–300 ms → 20–40 ms）。但那意味着和 vLLM 抢 SM，是**备选方案不是首选**。

预期：车牌场景 7.3 s → **0.6–1.2 s**。

#### T4. 超时分级与降级（0.5 天）

| 环节 | 超时 | 失败行为 |
|---|---|---|
| scene | 2 s | 返回 502 |
| detect | 5 s | 跳过检测器证据，`need_review=true` |
| binary/action | 3 s | 退回 6 类动作头 |
| OCR | 8 s | `fields=null` + `need_review=true` |
| 单图总预算 | 20 s | 立即返回部分结果 + `timeout=true` |
| 整单总预算 | 60 s | 返回已完成部分 + `partial=true` |

现在 `service_timeout=120s`、nginx `180s` —— 一个卡住的 OCR 就能挂满连接池 2 分钟。

#### T5. 上传限制与背压（0.5 天）

- 单图 ≤ 15 MB、总 ≤ 60 MB、`MAX_PHOTOS` 从 40 降到 **20**（40×手机原图 ≈ 200 MB 常驻内存）。
- `Image.MAX_IMAGE_PIXELS = 50_000_000`（防解压炸弹）。
- 内容类型白名单：`image/jpeg, image/png, image/webp, image/heic`。
- 超限返回 413 并带可读中文原因。

### 6.3 预期结果（需压测验证，不是承诺）

| 场景 | 现状（M1 MPS，4 并发） | 改造后（L20 共享 GPU 5，估算） |
|---|---|---|
| 单图 P50 | 592 ms | 130–180 ms |
| 单图 P95 | 7.3 s | 0.8–1.2 s |
| 单图 P99 | — | 1.5–3 s（取决于 vLLM 尖刺） |
| 吞吐 | ~2 图/s | 8–12 图/s |
| GPU 占用 | — | < 4 GB 显存，单次前向 <10 ms |

**容量判断**：工单按 5 图算，1000 单/天 = 5000 图/天 ≈ 0.06 图/s 均值。就算峰值放大 20 倍也只有 1.2 图/s。**你们的量级根本不需要"高并发"，需要的是把 P95 长尾砍掉**。

真到了 10 图/s 以上：先加 `ocr` 副本（CPU 便宜且线性），视觉侧再绑第二张卡（GPU 2/3/4 还有 16–19 GB 空闲）。视觉单实例在共享卡上跑到 ~15 图/s 之前，都不用扩。

**这三个数是估算，必须由 §13 的压测替换。** 尤其 P99——共享卡上它完全取决于同卡 vLLM 的负载曲线，`nvidia-smi dmon` 的实测数据才是唯一依据。

## 7. 安全

内网不等于安全——同网段任何机器都能打这个接口，而它会把工单照片里的 **VIN、车牌、里程**原样返回。

| 项 | 要求 |
|---|---|
| API Key | 每个上游一个 key，`X-API-Key` 头，`secrets.compare_digest` 比较；key 存 `.env.prod`（`chmod 600`） |
| IP 白名单 | nginx `allow <上游网段>; deny all;`，只放行上层应用 |
| CORS | `/v1/*` **删掉** `allow_origins=["*"]`；`/ui/` 若保留，限定内网源 |
| OpenAPI | 生产 `FastAPI(openapi_url=None, docs_url=None, redoc_url=None)` |
| `/metrics` | 不放公网入口；`location /metrics { allow 127.0.0.1; allow <监控网段>; deny all; }` |
| 上传 | 见 T5；**不落盘原始图**（当前也没落，保持一致） |
| 日志脱敏 | 日志里有 VIN/车牌，目录 `750`、文件 `640`，属主 `appuser` |
| TLS | 内网可先不上；若经过公司骨干网，用内部 CA 签一张，Caddy 自动续期更省事 |

**API Key 校验位置**：在 `app/main.py` 加中间件（比 `Depends` 更省事，能覆盖 `/metrics` 以外所有路径），并给 `/healthz` 开白名单（健康检查不该带 key）。

## 8. 日志与可观测

你们的诉求是"日志写成文件"，那就不引 Loki/ES，用**结构化 JSONL + 系统级轮转**，够用且零依赖。

### 8.1 两类日志

**A. 请求流水** `logs/api/access-YYYY-MM-DD.jsonl`，每请求一行：

```json
{"ts":"2026-11-12T18:30:01.234+08:00","request_id":"a1b2c3","endpoint":"/v1/analyze",
 "work_order_id":"IKD2045720261106001","filename":"接车.jpg","status":200,
 "latency_ms":187,"scene":"arrival_plate","scene_conf":0.94,"need_review":false,
 "model_version":"v5.0.0","client_ip":"10.51.x.x","api_key_id":"app-prod"}
```

**B. 结果流水** `logs/results/result-YYYY-MM-DD.jsonl`：完整响应体（含 `fields`、`review_reasons`、`latency_ms`），一图一行。这是你们日后复盘和回流黄金集的唯一依据。

**C. 错误流水** `logs/errors/error-YYYY-MM-DD.jsonl`：异常栈 + 入参摘要（不含图片 base64）。

### 8.2 落地方式

- 应用内写**按天滚动**的文件（自己实现 20 行即可：`datetime.date()` 变化时切文件），目录挂载 `./data/logs:/var/log/spmcv`。
- 同时保留 stdout（uvicorn 默认），供 `docker logs` 快查。
- Docker 层限制大小，防磁盘打满：
  ```yaml
  logging:
    driver: json-file
    options: { max-size: "50m", max-file: "5" }
  ```
- 宿主 logrotate（`/etc/logrotate.d/spmcv`）：
  ```
  /data/spmcv/data/logs/*/*.jsonl {
      daily
      rotate 30
      compress
      delaycompress
      missingok
      notifempty
      copytruncate
  }
  ```

### 8.3 指标（可选，但强烈建议）

现在 `app/metrics.py` 是进程内 `deque`，多 worker 下语义错误（见 §4）。改成单 worker 后**语义正确**了，但多副本仍会各自统计。

- 短期：nginx 侧 `stub_status`（连接数/请求数）就够了，够判断"是不是堆了"。
- 中期：每个 api 副本暴露 `/metrics`，Prometheus 按 `instance` 分别抓，聚合时用 `sum by (__name__)`；vision/ocr 也加 `/metrics`（GPU 利用率用 `nvidia_gpu_exporter`）。
- 告警三条就够：**5xx 率 > 1% 持续 5 min**、**P95 > 1.5 s 持续 10 min**、**GPU 空闲显存 < 2 GB**。

### 8.4 健康检查拆两个

| 路径 | 语义 | 内容 |
|---|---|---|
| `/healthz` | liveness，进程活着 | 恒 `200 {"ok":true}`，**不查下游** |
| `/readyz` | readiness，能接流量 | 权重已加载 + sha256 匹配 + dummy 推理成功 + 下游可达 + GPU 可用 |

**已实现（2026-11-13）**：

| 端点 | 行为 |
|---|---|
| `/healthz` | 只返回 `{"ok": true, "version": ...}`，**不碰任何下游**，实测 50ms |
| `/readyz` | 探测 vision / ocr（2s 超时），任一不可达返回 **503**；KEV 关闭时直接 `disabled: true`，不发请求 |

`vision_service._load_models()` 现在**权重缺失直接抛异常**，容器起不来而不是"健康地返回垃圾"；
设置了 `MODEL_DIR` 时还会在启动阶段校验 `manifest.json` 里的 sha256。

⚠️ **compose 的健康检查仍然应该打 `/healthz`，不是 `/readyz`**：
`/readyz` 反映的是下游可用性，用它当 healthcheck 会让 OCR 抖一下就把 api 容器重启——
这是典型的 liveness/readiness 误用。`/readyz` 留给负载均衡或 K8s readinessProbe。

## 12. 升级与回滚

**升级**（镜像 tag 即版本）：

```bash
# 服务器
docker compose down
docker load -i images/v3.1.0.tar          # 或 docker compose pull
sed -i 's/v5.0.0/v5.1.0/' .env.prod
docker compose --env-file .env.prod up -d
# 冒烟 + 观察 5xx / P95 30 分钟
```

**回滚**（≤ 2 分钟）：

```bash
sed -i 's/v5.1.0/v5.0.0/' .env.prod
docker compose --env-file .env.prod up -d
```

**规则**：
- 服务器上**永远保留上一个版本的镜像 tar**，不要 `docker image prune -a`。
- 模型和代码**同 tag 一起回滚**，不单独换权重。
- 大版本变更先在 `8081` 起一套影子服务，用真实流量回放（`scripts/eval_endpoint.py --replay`）对比，再切主。

## 13. 压测与验收清单

### 13.1 压测

```bash
# k6 或 locust，4 并发 / 8 并发 / 16 并发三档
k6 run --vus 8 --duration 5m script.js
```

必须记录的：P50 / P95 / P99、吞吐、GPU 利用率（`nvidia-smi dmon`）、CPU、内存、错误率。

```bash
# 压测时同步采 GPU 与线程数据，用于判定"是不是被同卡 vLLM 撞了"
nvidia-smi dmon -s um -d 1 -o T > /data/spmcv/data/gpu-dmon.csv &
k6 run --vus 8 --duration 5m script.js
```

**关键判据不是"最大 QPS"，而是"P95 在目标并发下是否守住 1.2 s，且 P99 没有失控到 4×P50"**。

三档并发都要测，因为共享卡上并发升高会放大尖刺：4 / 8 / 16。若 8 并发达标但 16 并发 P99 崩到 8 s，说明瓶颈是 GPU 排队而不是 OCR——此时加 api 副本没用，得降 batch 或加第二张卡。

### 13.2 上线验收（全绿才放行）

| # | 项 | 判据 |
|---|---|---|
| 1 | 单测 | `pytest tests -q` 全绿（当前 54 个，0.31 s） |
| 2 | 精度回归 | `eval-val` 各项不低于 §2.2 下限 |
| 3 | 规格样例 | `eval-spec` 12/12 |
| 4 | ONNX 等价 | 与 `.pt` top1 逐张一致率 ≥ 99% |
| 5 | 延迟 | 8 并发 P95 ≤ 1.2 s；16 并发 P95 ≤ 2 s |
| 6 | GPU 争抢 | 压测期间 P99 ≤ 4×P50，否则按 §3.3 判定表处理 |
| 7 | 线程不超订 | 容器内 `ps -eLf \| wc -l` 与 `nproc` 同量级，不是 1600+ |

## 14. 运维 runbook

| 症状 | 首查 | 处置 |
|---|---|---|
| 502 / 503 | `docker compose ps`、`/readyz` | 权重缺失 → 查 `MODEL_DIR`、manifest sha256 |
| P95 突然翻倍 | `nvidia-smi dmon` 看 GPU 5 的 `sm` 列 | 同卡 vLLM 在跑长生成；临时降 `VISION_MAX_BATCH` 到 4 |
| P99 长期 > 4×P50 | 同卡 vLLM 的负载曲线 | 带着 `dmon` 数据申请独占卡，这是唯一根治办法 |
| GPU OOM | `nvidia-smi` 进程列表 | 别人扩了 vLLM；`VISION_MEM_FRACTION` 兜底 |
| CPU 跑满、OCR 变慢 | `top -H`、`ps -eLf \| wc -l` | 线程超订：确认 `OCR_INTRA_OP_THREADS=4` 已生效 |
| 日志磁盘满 | `du -sh data/logs` | 检查 logrotate；`max-file` 是否生效 |
| 内存涨到 OOM | 单次请求图片数 | 20 张上限 + 超时是否生效 |
| 复核率异常升高 | `logs/results` 里 `review_reasons` 分布 | 通常是预处理/OCR 退化，回滚 tag |
| 504 网关超时 | nginx `error.log`、api 在途数 | 上游慢，查 vision/ocr 队列深度 |
| 模型加载 2 分钟 | 启动日志 | 首次 cuDNN autotune，属正常；`start-period=120s` 已覆盖 |

## 15. 风险登记

| 风险 | 等级 | 影响 | 缓解 |
|---|---|---|---|
| **AGPL 许可** | 高 | 对外交付法务风险 | ONNX 化（§5.1）或 RT-DETR 重训 |
| **无法独占 GPU** | 高 | P99 被同卡 vLLM 尖刺波及 | 绑 GPU 5 + 显存限额 + batch 可调；用 `dmon` 数据说话 |
| **同卡 vLLM 对方扩容** | 中 | 我们被 OOM 杀掉 | `VISION_MEM_FRACTION=0.35` + `restart: unless-stopped`，崩了 10 s 内自愈 |
| **git 零提交** | 高 | 无法回滚 | 首日建基线 |
| **权重靠 `.env` 路径拼** | 高 | 同代码不同产品 | manifest + 进镜像 |
| 精度阈值靠经验调 | 中 | 换环境后复核率漂移 | 上线后用真实工单统计复核率，再调 `WEAK_SCENE_CONF` |
| 服务单 VIN 仅尾段 | 中 | 自动通过率上不去 | 已用 `vin_partial` + 复核兜底，不编造 |
| 单机无冗余 | 中 | 宕机即停服 | 计划内重启窗口 + 快回滚；不建议为它上 K8s |
| 无数据库 | 低 | 事后查证只能靠日志 | JSONL 保留 30 天 + 关键结果进 `results/` |

## 17. 已确定 / 仍待确认

### 已确定（v1.1 更新）

| 项 | 结论 | 影响 |
|---|---|---|
| CPU / 内存 / 磁盘 | 208 核 / 1 TiB / `/data` 795 GB | OCR 走 CPU 8 worker，不上 GPU（§3.4） |
| 独占 GPU | **不可行** | 绑 GPU 5，P95 目标放宽到 1.2 s（§3.3） |
| 上游超时 | 暂不约束 | 保持同步接口，不做 `202 + job_id`；整单预算 60 s 由我们自己兜住 |

### 仍待确认

1. **同机 vLLM 的峰值时段**：决定压测时间窗，也决定 P99 承诺能不能写进 SLA。最好能问一句"哪几个小时 GPU 最忙"。
2. **能否让 vLLM 侧限制 `gpu_memory_utilization`**：不限制的话，对方扩容时我们会 OOM。虽然 `restart: unless-stopped` 能自愈，但请求会掉。
3. **峰值 QPS 与单次调用图片数**：现在按"≤ 12 图/s、单工单 5–12 图"设计。
4. **原始图片是否必须留存**：当前方案不存图（只存日志）。若业务需要"调出当时的照片"，要补 MinIO 或本地目录 + 生命周期。
5. **`/ui/` 是否保留**：现在有一个单页前端。若只给上层应用调用，生产环境建议直接关掉 `/ui/`，少一个攻击面，也少一份 CORS 配置。
